# 模块 11 · token 估算与 80% 提醒

> 源码：`src/core/tokens.ts` + `src/ui/UsageBar.tsx`
> 题面位置：等级 2「上下文过长提醒」——"**待发送内容达到设置的 80% 时，提示"上下文快满了，可以排除较早的消息"。提醒至少显示当前用量、上限和可处理的消息入口。**"

## ① 这段在干什么

1. **估算**每次装配的 token 量（`totalTokens = Σ parts.tokens`）；
2. 在输入框上方显示一条**用量条**：`上下文 X / Y（Z%）`；
3. 当 `Z% >= contextWarnPct`（默认 **80**）时，条变成警示样式，并**多出一个「去处理消息」按钮**
   —— 这就是题面要求的"**可处理的消息入口**"。

## ② 关键设计决策 + 为什么

### 2.1 估算公式：CJK 按 1、其他按 4 字符 1 token

```ts
export function estimate(text: string): number {
  let cjk = 0, other = 0;
  for (const ch of text) { CJK.test(ch) ? (cjk += 1) : (other += 1); }
  return Math.ceil(cjk + other / 4);
}
```

**为什么按字符类分而不是统一按 4 字符 1 token**：模型对 CJK 的分词密度远高于拉丁字母。
统一按 4 字符估，中文上下文会被**系统性低估约 3–4 倍**，
结果是"看起来才用了 20%、其实早就爆了"，80% 提醒永远不出现。
反过来按 1 字符 1 token 估英文又会高估。**分类估算**是这个精度/成本权衡下的合理选择。

**README 明确声明这是"估算"**：不引入 tokenizer 依赖（PLAN §2.2 的依赖上限），
所以它是一个**数量级正确**的近似，不承诺与任何具体模型的 tokenizer 对齐。
CJK 判定用一个宽字符类正则（含中日韩统一表意文字、假名、全角标点等区段），
`for...of` 按**码点**遍历，避免代理对被当成两个字符。

### 2.2 预算：`floor(contextLimit * worldBookBudgetPct / 100)`

世界书另有一条**配额**（默认 25%）。它和提醒是配套的：
提醒告诉你"上下文快满了"，预算则保证"世界书这一段不会一家独大"。
`worldBookBudgetPct = 100` 即等价于**关闭**这条机制。
（再强调一次：**预算是本项目自引入的**，题面规则 5 并没有要求它。）

### 2.3 🔴 阈值判定以**快照**为准，不以预览为准

题面原话只说"待发送内容达到设置的 80% 时"。但"待发送内容"在生成期间是**会变的**
（用户在输入框里继续打字）。如果拿"当前输入框"当作判据，就会出现：
"生成到一半，提醒条自己亮了/灭了"，而这次请求其实早已冻结。

所以本项目定了一条口径（写进 README）：

- **预览时的百分比只是预估**，用来提前提示；
- **权威判据 = 发送瞬间冻结的快照**：`RequestSnapshot.totalTokens / contextLimit >= contextWarnPct/100`；
- 发送后按**最新一次快照**重算提醒条。

也正是这条口径，把"提醒"和"世界书预算"绑在了一起 ——
超预算的条目会在快照里留下 `budget_exceeded` 痕迹，让"为什么这次少了一段背景"可被解释。

### 2.4 判据是**整数百分比**，不存在 `0.8` 这种小数口径

```ts
const pct = limit > 0 ? Math.round((used * 100) / limit) : 0;
const over = limit > 0 && pct >= warnPct;     // warnPct 是 80 这样的整数
```

统一成"整数百分比比较"，避免出现"`0.7999 >= 0.8` 为假"这种边界抖动，
也保证 UI 上显示的 `80%` 与触发条件**是同一个数**（显示 80% 就一定已触发）。

### 2.5 提醒条必须带"可处理的消息入口"

`UsageBar` 在 `over` 时渲染一个「去处理消息」按钮，点击后把聊天列表滚到顶部
（`document.querySelector('.chat-list').scrollTo({top:0, behavior:'smooth'})`），
让用户立刻看到"较早的消息"并可以选中批量排除。
配合消息工具条的"只选用户消息 / 只选 AI 消息 + 批量不进上下文"，
从"看到提醒"到"真的把上下文降下来"是**三步之内**的事。

## ③ 可能被追问的问题

**Q1：为什么不装一个真正的 tokenizer？**
两个原因：① PLAN §2.2 的依赖上限只允许 `react` + `react-dom`（运行时）；
② "用哪个 tokenizer"本身就是错的 —— 用户可以在面板里填**任意**服务地址与模型，
每个模型的 tokenizer 都不同，装一个只对一个模型准。**估算 + 明确声明是估算**才是诚实且通用的做法。

**Q2：估算不准会不会导致 80% 提醒误导用户？**
会有一个数量级的把握，不会精确。所以：① 文案写的是"**估算** X / Y"；
② 判据用整数百分比，且 UI 上显示的数就是判据用的数；③ README 里如实声明。
如果真要精确，正确做法是把服务端返回的 `usage.prompt_tokens` 回填 —— 
本项目**已经在流式响应里看得到 `usage`**，但把它接进提醒条属于"精度提升"而非正确性修复，
因此没有做（不引入未验证的复杂度）。

**Q3：`totalTokens` 里包含什么？**
`parts` 各项 `tokens` 的**和**，即：角色卡 + 预设 system 模块 + 世界书激活内容 + 历史消息 +
本次待发送输入 + preset post-history 模块。**包含世界书超预算的那行提示文字**
（因为它确实会随请求发出去）—— 这是刻意保持一致：显示的用量 = 实际会发的内容量。

**Q4：世界书预算超了，会不会让"上下文使用率"看起来正常其实内容被砍了？**
不会看不到。超预算会在两处留痕：
① 预览/快照的 `worldbook` 部分末尾有"（世界书预算已满，共 N 条未插入）"；
② 检查视图的"未发送原因"里逐条列出 `budget_exceeded`。

**Q5：`contextLimit` 是模型的真实上限吗？**
不是自动探测的，是**用户在会话设置里填的**（默认 32768）。因为这个应用要能接任意服务地址，
无法可靠地自动探测上限；由用户声明"我认为这个模型能吃多少"是唯一稳妥的做法。
设置面板里那一项就叫"上下文上限（估算 token）"，没有假装它是模型元数据。

**Q6：为什么提醒条要在"发送前预览"里也出现？**
题面只说"提醒至少显示当前用量、上限和可处理的消息入口"，没说位置。
本项目两处都放（输入框上方 + 预览面板顶部的统计行），
因为"发现快满了"这件事应该发生在**决定要不要发送之前**。
`RequestPreview` 顶部那行 `估算 X / Y（Z%）` 与 `UsageBar` 用的是**同一份** `buildRequest()` 结果。
