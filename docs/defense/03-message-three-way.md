# 模块 03 · 消息三分离（界面隐藏 / 不进上下文 / 删除）

> 源码：`src/core/types.ts`（数据）· `src/state/store.tsx`（写）· `src/ui/MessageBubble.tsx` + `MessageToolbar.tsx`（交互）
> 测试：`tests/assembly.test.ts` `#8` `#9` · 题面位置：`docs/problem-statement.md` §0.1

## ① 这段在干什么

题面最重的一句话之一：

> **"从界面折叠，不进入上下文，删除消息，是三种操作。请在数据和交互中区分它们。"**

本项目把它落成**三种彼此不同的机制**，不是一个布尔开关的三种叫法：

| 操作 | 数据改动 | 影响渲染 | 影响发给 AI | UI 表现 |
|---|---|---|---|---|
| **界面隐藏** | `message.uiHidden = true` | ✅ 折叠/隐藏 | ❌ **完全不影响** | 消息变半透明；顶部「显示已隐藏消息」开关可以找回来 |
| **不进上下文** | `message.excluded = true` | ❌ 仍正常显示 | ✅ 不参与装配 | **留在原位**，左侧色条 + 标签「未发送给 AI」 |
| **删除** | `repo.deleteMessage(id)` —— **从 IndexedDB 真删** | ✅ 消失 | ✅ 不再存在 | 二次确认弹窗，文案明确说"和隐藏/排除不同" |

两种标记**视觉上必须不一样**（题面原话"让用户能看出哪些消息只是没显示，哪些消息没有发给 AI"）：
`uiHidden` 是**半透明 + 「已隐藏」灰 chip**；`excluded` 是**左侧橙/红色条 + 「未发送给 AI」chip**。

## ② 关键设计决策 + 为什么

### 2.1 为什么必须是两个字段，而不是一个枚举

一个 `visibility: 'normal' | 'hidden' | 'excluded'` 的枚举**表达不出**"既隐藏、又排除"。
而这是**合法且常用**的状态：这条消息我又不想看、也不想让 AI 读。用两个独立布尔，
四种状态（正常 / 只隐藏 / 只排除 / 两者都是）**天然可表达**，不需要额外约定。

### 2.2 为什么删除必须是真删（✅ 关键取舍）

题面点名"**删除是另一个操作，不要用删除代替隐藏或排除**"。
反向的仿冒同样要不得：如果删除只是把 `excluded` 置 true，会出现两个问题：

1. **数据还在** —— 用户的"删除"意图没被尊重（隐私 / 清理诉求）；
2. **语义污染** —— 检查视图里会冒出一堆"被排除的消息"，把真正的排除决策淹没。

所以删除走**真删链**：`store.removeMessages(ids)` → `repo.deleteMessages(ids)` → `idbDeleteMany('messages', ids)`，
**真的从库里抹掉**（`src/state/store.tsx:356` → `src/storage/repo.ts:117` → `src/storage/idb.ts:100`），
并在 UI 上给**不可逆的二次确认**（`window.confirm`，文案写明"无法恢复"，
且提示"如果只是不想让 AI 看到，请用「不进上下文」"）。

### 2.3 装配层**不读** `uiHidden`（结构性保证）

```ts
if (msg.excluded) continue;
if (msg.status !== 'complete') continue;
```

`buildRequest()` 里**没有**任何一处提到 `uiHidden`。这不是"记得别写"，而是**代码里根本没有这个变量**——
从结构上排除"隐藏影响上下文"的可能。世界书引擎同理（`activateWorldBook` 的 `eligible` 过滤也只看这两个字段）。

**测试**：`#8 uiHidden 的消息仍然参与装配`、`#9 excluded 的消息不参与装配，并记入 skipped`。

### 2.4 批量与筛选（题面要求"支持单条操作，也支持批量处理"）

`MessageToolbar` 提供：全选 / 取消选择 / **只选用户消息** / **只选 AI 消息** →
批量隐藏 / 批量取消隐藏 / 批量不进上下文 / 批量加回上下文 / 批量删除。
实现上是把选中的 id 集合交给 `setMessageFlags(ids, patch)`，一次事务批量落库（`idbBulkPut`），
**先 await 落库完成、再 dispatch 更新内存镜像** —— 避免"刷新后状态回退"。

### 2.5 编辑只改 `content`，不动 `id` / `seq`

`editMessage(id, content)` 只替换正文字段。为什么这个细节重要：
`seq` 是会话内单调序号、也是世界书扫描集的排序键，一旦编辑就改 `seq`，
"这次待发送的消息只装配一次"（模块 02 §2.3）的判据就失效了。

编辑的是**含 `<tavern-panel>` 标签的原始正文**（存储层永远保存原文），
这样渲染失败也不会丢内容，改也改得动。

## ③ 可能被追问的问题

**Q1：隐藏了一条消息，预览里还能看到它，那隐藏有什么用？**
这正是题面要的效果：**隐藏只解决"我不想看"，不解决"我不想发给 AI"**。
两个诉求经常同时存在（比如一条很长的 OOC 讨论），所以两个操作都得有、且互不干扰。
演示时的杀手级对比就是：**隐藏一条 → 预览里它仍在；排除一条 → 预览里它消失。**

**Q2：删除以后，跟它有关系的快照怎么办？**
快照**不动**。快照是"那一刻发送了什么"的历史记录，用户删掉今天的消息不应改写昨天的发送记录——
这与"已发送的快照不能被后续编辑改写"（模块 04）是同一条原则。
只有删**整个会话**时，才会级联删掉该会话的 messages 与 snapshots（`deleteSessionCascade`）。

**Q3：`excluded` 的消息还能被世界书关键词命中吗？**
不能。装配和扫描集用的是同一套过滤条件（`excluded === false && status === 'complete'`），
所以被排除的消息既进不了上下文，也进不了世界书扫描集。
如果一个关键词只出现在被排除的消息里，对应条目就是 `no_keyword_match`。

**Q4：能不能"删除"但保留内容（软删除）？**
不做。软删除一旦存在，"删除"和"不进上下文"在数据层就变得难以区分 —— 正是题面要避免的混淆。
需要保留内容时，正确的操作是 `excluded`（正文仍然保存，随时可以重新加入上下文）。

**Q5：批量操作的原子性怎么保证？会不会删一半？**
批量写走**同一个 IndexedDB 事务**（`idbBulkPut` / `idbDeleteMany`），事务要么整体提交、要么整体回滚；
`await txDone(tx)` 之后才 dispatch 内存更新。所以不存在"页面上显示删了、库里还在"的中间态。

**Q6：`uiHidden` 的"显示已隐藏消息"入口在哪、状态存哪？**
入口在消息工具条最左边（`MessageToolbar` 的「显示已隐藏消息」勾选框）。
它是**纯视图状态**（`ChatView` 内的 `useState`），**不落库** —— 因为它只影响"这一刻你怎么看"，
刷新后回到默认（隐藏的折叠起来）。这是个刻意的取舍：视图偏好不该写进业务数据里。
